## TL;DR

In this walkthrough, you will test a Go REST API powered by **Gin** and **MongoDB** without writing a single test file, interface wrapper, or mock by hand.

1. **Record:** Keploy listens to live network traffic via Linux eBPF, saving both incoming HTTP requests and outgoing MongoDB wire queries into human-readable YAML.
2. **Replay:** Keploy acts as a virtual mock server, replaying recorded test cases completely offline in under 8 seconds—without spinning up a real MongoDB instance.
3. **Catch Regressions:** When an API contract or database query changes unintentionally, Keploy immediately flags the exact response mismatch with a visual diff.

---

## Why Keploy? (The Integration Testing Dilemma)

If you build backend services in Go, you already know the testing spectrum dilemma:

* **Unit tests are fast, but shallow:** Mocking MongoDB using interfaces or libraries like `gomock` or `testify` requires hundreds of lines of boilerplate. Worse, hand-crafted mocks frequently drift away from the actual database behavior.
* **End-to-end integration tests are realistic, but heavy:** Spinning up ephemeral databases, seeding test fixtures, resetting state between tests, and managing tear-down scripts makes test suites slow, fragile, and difficult to maintain in continuous integration (CI) pipelines.

```
+-------------------------------------------------------------+
| Traditional Testing Pain:                                    |
| Hand-written mocks drift  <--->  End-to-End tests are flaky |
+-------------------------------------------------------------+
                              ↓
+-------------------------------------------------------------+
| The Keploy Solution:                                        |
| 1. Capture real network calls (HTTP + MongoDB)              |
| 2. Replay tests against isolated app using auto-mocks       |
+-------------------------------------------------------------+
```

**Keploy solves this by recording live application interactions.** It captures the HTTP request, the outgoing database queries, and the exact response. When you run `keploy test`, it re-runs your application binary in a sandbox, intercepts outgoing network queries, and serves the recorded responses as virtual mocks.

<Callout type="info" title="What is a Virtual Wire Mock?">
Unlike traditional mocking libraries that replace Go functions or interface implementations inside your code, Keploy mocks interactions at the network socket layer. Your application code remains 100% standard Go—no SDK imports, no wrapper interfaces, and no dependency injection hacks required.
</Callout>

---

## How It Works: Record vs. Replay

Keploy operates in two distinct execution modes:

1. **Record Mode (`keploy record`):** You run your Go application through Keploy. As client traffic hits your API endpoints, Keploy transparently captures incoming HTTP payloads and all corresponding outgoing MongoDB operations into a versioned YAML test suite.
2. **Replay Mode (`keploy test`):** Keploy boots your Go application, replays the recorded HTTP requests, and intercepts any database calls, serving the previously recorded BSON responses. It compares the newly returned HTTP response with the recorded response and produces a regression pass/fail report.

## Step-by-Step Tutorial

<Steps>

<Step title="Install the Keploy CLI" id="step-1-install-keploy">

Download and install the official Keploy CLI binary onto your machine:

```bash
curl --silent -O -L https://keploy.io/install.sh && bash install.sh
```

Verify that the installation was successful by checking the CLI version:

```bash
keploy --version
```

You should see output similar to `keploy: version v2.3.0`.

<Callout type="info" title="Why does Keploy need elevated privileges (sudo)?">
Keploy uses Linux eBPF (Extended Berkeley Packet Filter) to attach hooks to kernel network socket operations. This allows it to capture and redirect TCP packets between your Gin application and MongoDB without altering your application binary. On Linux and WSL2, creating eBPF maps requires administrative privileges (`sudo`).
</Callout>

</Step>

<Step title="Tour the Go Gin Sample Application" id="step-2-tour-the-sample-app">

For this guide, we use the official **Gin + MongoDB URL Shortener** sample application. The application provides three primary HTTP routes:

* `POST /url`: Accepts a long URL in JSON format, computes an 8-character base58 hash, saves the record into MongoDB, and returns the shortened link.
* `GET /:param`: Accepts a shortened hash slug, queries MongoDB for the corresponding original link, and issues an HTTP `303 See Other` redirect.
* `GET /verify-email`: Validates email syntax using the `emailverifier` package.

Notice the structure of `backend/main.go` and `backend/handler.go`:

```go
// backend/main.go
package main

import (
    "github.com/gin-gonic/gin"
)

func main() {
    dbName, collection := "keploy", "url-shortener"
    client, err := New("localhost:27017", dbName)
    if err != nil {
        logger.Fatal("failed to connect to mongodb", zap.Error(err))
    }

    r := gin.Default()
    r.GET("/:param", getURL)
    r.POST("/url", putURL)
    r.GET("/verify-email", verifyEmail)

    r.Run(":8080")
}
```

Notice what is missing: **There are zero Keploy imports or SDK dependencies in the application code.** The service is pure, idiomatic Go.

</Step>

<Step title="Launch the MongoDB Dependency" id="step-3-start-mongodb">

Before recording test cases, we need a live database instance for the application to interact with. Use Docker Compose to launch MongoDB in the background:

```bash
cd backend
docker compose up -d mongoDb
```

Verify that the MongoDB container is running and healthy:

```bash
docker ps --filter "name=mongoDb"
```

<Callout type="danger" title="Avoid Port Collisions">
Ensure that no local MongoDB instance is already running natively on port `27017`. If port `27017` is occupied, the Docker container will fail to bind to the host network.
</Callout>

</Step>

### Examining a Generated Test Case (`test-1.yaml`)

Each test case contains the exact request sent, the expected response, and an `assertions.noise` block:

```yaml
version: api.keploy.io/v1beta1
kind: Http
name: test-1
spec:
  req:
    method: POST
    url: http://localhost:8080/url
    header:
      Content-Type: application/json
    body: '{"url": "https://google.com"}'
  resp:
    status_code: 200
    body: '{"ts":1718943885198315028,"url":"http://localhost:8080/Lhr4BWAi"}'
  assertions:
    noise:
      body.ts: []
      header.Date: []
```

<Callout type="info" title="Automatic Noise Filtering">
Notice `assertions.noise`: Real-world APIs return dynamic timestamps (`ts`) and `Date` headers that vary with every invocation. Keploy automatically flags changing fields as noise so that future test replays assert schema correctness without causing false test failures.
</Callout>

### Examining the Recorded Mocks (`mocks.yaml`)

Inspect `backend/keploy/test-set-0/mocks.yaml`. You will see the raw MongoDB wire query captured during test recording:

```yaml
version: api.keploy.io/v1beta1
kind: Mongo
name: mock-0
spec:
  metadata:
    operation: update
  requests:
    - message:
        sections:
          - body: '{"update":"url-shortener","updates":[{"q":{"_id":"Lhr4BWAi"},"u":{"$set":{"url":"https://google.com"}}}]}'
  responses:
    - message:
        sections:
          - body: '{"n":1,"nModified":0,"upserted":[{"index":0,"_id":"Lhr4BWAi"}],"ok":1.0}'
```

<Callout type="warning" title="Sanitizing Recorded Mocks Before Git Commit">
Because Keploy captures real network packets, recorded mocks and test cases will contain actual data payloads. Ensure that you never record sensitive credentials, production secrets, or private API keys without sanitizing `mocks.yaml` before committing to version control.
</Callout>

<Step title="Break Contract on Purpose (The Regression Diff)" id="step-7-break-something-on-purpose">

To see how Keploy guards against accidental breaking changes, let us intentionally introduce a regression into the handler.

Open `backend/handler.go` and locate the `putURL` handler. Change the response JSON key from `"url"` to `"short_url"`:

```diff
  c.JSON(http.StatusOK, gin.H{
      "ts":  time.Now().UnixNano(),
-     "url": fmt.Sprintf("http://localhost:8080/%s", id),
+     "short_url": fmt.Sprintf("http://localhost:8080/%s", id),
  })
```

Save the file and re-run `keploy test`:

```bash
sudo keploy test -c "go run main.go handler.go" --delay 5
```

Keploy immediately flags the breaking change and prints an actionable diff:

## Troubleshooting Common Gotchas

| Issue | Root Cause | Solution |
|---|---|---|
| `permission denied (eBPF map create)` | Keploy executed without administrative rights. | Prefix commands with `sudo keploy ...` on Linux/WSL2, or grant container capability `CAP_SYS_ADMIN`. |
| `connection refused :8080 during test` | Keploy fired test requests before Gin completed port binding. | Add `--delay 5` or `--delay 10` to `keploy test` to allow sufficient boot time. |
| `connection refused to 27017` during record | MongoDB container was not started prior to recording. | Run `docker compose up -d mongoDb` and check container health with `docker ps`. |
| `Dynamic timestamp mismatch in test` | Nonce, timestamp, or UUID changed in response body. | Add the field path (e.g. `body.my_timestamp`) under `assertions.noise` in the test YAML file. |

## Where Keploy Fits in Your Stack

Keploy is not meant to replace unit tests entirely; rather, it occupies a high-value sweet spot in modern testing strategies:

```
                  /\
                 /  \
                / E2E\        <-- Slow, flaky, expensive
               /------\
              / Keploy \      <-- Fast, zero-code, auto-mocked integration tests
             /----------\
            / Unit Tests \    <-- Fast, isolated domain math/logic
           /--------------\
```

* **Where Keploy Shines:**
  * **Legacy Codebases:** Rapidly generate 80%+ test coverage across undocumented REST APIs in hours rather than months.
  * **Refactoring Safety Net:** Record current behavior, refactor internal architectures, and replay tests to guarantee zero unintended contract regressions.
  * **CI/CD Integration:** Run comprehensive integration test suites in GitHub Actions without deploying or paying for staging databases.
* **Where Hand-written Unit Tests Are Still Best:**
  * Complex computational algorithms and mathematical validation.
  * Edge cases that are difficult or impossible to trigger with real HTTP network traffic.
